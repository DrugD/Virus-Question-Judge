1. 系统是什么 / 评测流程

一个 基于 rubric 的科学问题（scientific question）LLM-judge 评测台。研究场景：给 agent 一份（脱敏的）研究数据， 让它读数据并提出 5 条科学问题；再用一个 judge LLM 按用户标注的 gold 评测标准给这些问题打分。 支持网页交互与无头批量两种入口。 

上传 data + gold ──▶ 脱敏 data ──▶ [agent 读数据出 5 题] 或 [judge-only：直接吃用户上传的候选 JSON]
                                         │
                                         ▼
                          judge 逐条按 rubric 打分（闭合 gold rubric）
                                         │
                       set-level Hit 判定（5 条里有没有任意一条过阈值 0.6）
                              ├─ Hit=✓ → 保留闭合分数
                              └─ Hit=✗ → 整组改判【开放 rubric】（相对数据评匹配度+合理程度）
                                         │
                                         ▼
                     leaderboard / Pass@1 / Pass@5 / Hit / 雷达 / CSV 导出

服务端入口：webapp.server:app（FastAPI + uvicorn，默认端口 8000）。前端是纯静态 SPA（无构建步骤，改完静态文件浏览器硬刷即可）。

2. 核心概念

2.1 两套 rubric

rubric触发维度（满分）composite阈值
闭合 closed 候选命中/对齐某条 gold 语义对齐 semantic_alignment 67 + 可接受度 acceptability 33 = 100 (67分项+33分项)/100；secondary gold 且存在 primary 时 ×0.85 0.6
开放 open 整集 5 条都没命中（Hit=✗，pass_count==0） 数据匹配度 data_match 50 + 科学合理性 soundness 50 = 100 (data_match+soundness)/100；无 centrality 惩罚 0.6

为什么要开放 rubric：闭合 rubric 下，未命中 gold 时 semantic_alignment=0，composite 上限仅 0.33，整组必挂——这是"惩罚未命中"而非"按开放科学问题自身价值评分"。 开放 rubric 改为相对原始数据评：① data_match=问题所涉对象/变量是否真实存在于数据、规模粒度是否足以研究（防刷分压舱维度）；② soundness=问题本身是否非平凡、逻辑自洽、可检验。

两套 rubric 的锚点（4 档分值 + 文字）都集中在 eval/metrics/gold_rubric_metric.py 与 eval/metrics/open_rubric_metric.py 顶部常量，judge prompt 与 UI 面板都从这里取，永远同步。

2.2 指标：Hit ≠ Pass@1（务必分清）

指标定义说明
Pass@1仅看 rank-1 那一条是否过阈值（1.0/0.0）对位置敏感，只认头名
Pass@5计数式：pass_count/5（每过 1 条 +0.2）与排名无关，看过了几条
Hit 命中率5 条里至少 1 条过阈值即 ✓对位置不敏感；开放 rubric 的触发条件就是 Hit=✗
Avg Comp / Avg Raw5 条 composite / raw 的均值leaderboard 头条分

例：rank-1 没过但 rank-3 过了 → Pass@1=0 而 Hit=✓。计算见 webapp/pipeline_runner.py::_pass_at_k_stats。

2.3 数据脱敏（desensitization）

agent 可见的数据目录会被脱敏：目录拍平、每个文件改名为 1.csv / 2.json / …（只保留扩展名），嵌套压缩包递归展开后内部成员同样改名。 目的：防止 agent 靠 43059586_RdRp_motif_collection.xlsx 这类含义文件名"白嫖"分数。

安全不变量：原名映射 filename_map.json 只写在 qset 根目录（judge-only），绝不能出现在 agent 可见的 raw_no_name/ 或 workspace 的 data/ 里——否则脱敏失效。 实现见 webapp/pipeline_runner.py::_desensitize_data / _expand_archives_in_place / hydrate_workspace。

脱敏对分数的真实影响（实测，invertebrate_rna_virosphere_2016）：脱敏前 Pass@1≈0.75，脱敏后≈0.4 —— 说明脱敏确实切断了文件名泄漏。

2.4 候选 JSON 契约（AgentOutput）

{
  "agent_id": "<label>",
  "questions": [ { "rank": 1, "question": "Does X drive Y in this dataset?" } ]   // 1..5 条，question 必须以 ? 结尾
}

也兼容纯字符串数组 "questions": ["...?"]；--strict 强制 5 条互异、rank 1..5。

6. 硬约束（动手前必读）

密钥安全：API token（NEWAPI_KEY 等）只能存在 .env（已 gitignore），绝不写进源码或 config.yaml。config 里 api_key_env 存的是变量名不是密钥。曾在明文出现过的 token 应由用户轮换。
脱敏不变量：filename_map.json 永远 judge-only（qset 根），不得进 agent 可见目录。见 §2.3。
Windows 环境：
  • 所有 python 调用前置 PYTHONUTF8=1；用 .venv-win/Scripts/python.exe（基础解释器 Python 3.11；PATH 上的 python 是 Windows Store 占位 stub，不可用）。
  • bash 是 Git Bash（Unix 语法，/dev/null、正斜杠）。
  • git 偶发 .git/index.lock: Invalid argument（IDE/fsmonitor 持锁）：在同一条命令里 rm -f .git/index.lock; git -c core.fsmonitor=false ...。
  • 本机 git 操作需禁用 sandbox（dangerouslyDisableSandbox: true）。
同步目标：推送到 DrugD/Virus-Question-Judge 的 sync-test 分支。提交信息以 Co-Authored-By: Claude ... 结尾。提交时只 stage 自己改的文件——.claude/settings.json 的改动是 harness 产生的，不要带上。

8. 给下一个 LLM 的话

  • 改 rubric 分数/锚点/措辞：只动 eval/metrics/{gold,open}_rubric_metric.py 顶部常量；judge prompt 与 UI 自动同步（UI 经 /api/rubric_definitions 取）。
  • 新加一条评分路径：注意有三处调用 score_against_gold + rescore_open_if_missed —— _run_one_agent、_run_judge_only（均在 pipeline_runner）、score_candidate（batch_judge）。改动要三处一致。
  • 结果行字段：闭合与开放都复用 GoldRubricResult，靠 rubric_kind 区分；scores 的 key 随 rubric 变（semantic_alignment/acceptability vs data_match/soundness）——前端取分时要看 rubric_kind。
  • 验证习惯：能用 --dry-run 和 fake judge 单测就别花 token；真 judge 跑批前先 dry-run 确认脱敏。
  • 动手前：确认是否需要进 worktree / 是否要推 sync-test；§6 的硬约束逐条遵守。
  • 更新本文件：完成里程碑后，往 §3 版本表加一行，并在相关章节增量更新；保持"读完即可接手"。
